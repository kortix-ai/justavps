Hard Constraints

  • Must be designed for bare metal.
  • Must scale from one host to huge fleets, clusters, regions, and ultimately millions of sandboxes.
  • Competitive boot/resume times across the board. Ideal: sub-1-second sandbox start/resume where technically possible, otherwise clearly benchmarked against Daytona/E2B/Modal-class products.
  • Final JustAVPS must be ours to run, modify, close-source, and commercialize. OSS code/forks/reference implementations may be used as a basis where the license allows.
  • Do not depend on a third-party hosted sandbox SaaS as the core runtime. Owning/forking/running OSS code ourselves is allowed if licensing works.
  • Runtime is open: MicroVMs, full VMs, containers, Linux containers, Kubernetes, Incus/LXD, Firecracker, Nomad, raw VPS automation, CubeSandbox, Daytona/E2B OSS code, or anything else.
  • Preference: strong isolation / isolated-kernel designs (MicroVMs/VMs) if boot times and density work. Shared-kernel containers allowed if you can justify the security/scale tradeoff.
  • Architecture must not block future GPU support.
  • Final result must be deployed for real, not localhost-only.
  • Core flows must be proven with tests or repeatable verification.

Core Problem

Build the mechanisms that make a complete cloud runtime for long-running developer/AI-agent machines possible.

Provisioning

  • create isolated Linux machines/sandboxes
  • choose CPU/RAM/disk/resources
  • place on healthy hosts
  • inject SSH keys/config/secrets safely
  • track provisioning states and clean up failures

Templates / Images

  • base Linux images
  • developer/agent templates
  • custom images if possible
  • image caching/materialization on hosts
  • versioning or content identity
  • fast create from template

Fast Start / Resume

  • fastest possible cold starts
  • ideal sub-1-second start/resume path
  • warm pools, pre-cached images, pre-warmed kernels/VMs/containers, lazy loading, or any mechanism that gets competitive boot times
  • benchmark boot/start/resume against the chosen reference systems
  • clear running/stopped/resuming/error states

Persistence

  • durable filesystem/disk
  • long-running processes
  • stable SSH/proxy access
  • identity survives stop/start/reboot
  • economics for running vs stopped machines

Snapshots / Restore / Clone

  • snapshot a machine
  • restore a machine
  • clone a new machine from snapshot
  • promote useful snapshots into templates if possible
  • safe, trackable, storage-aware snapshots

Archive / Offload

  • archive stopped/inactive machines
  • offload state to cheaper storage
  • rehydrate archived machines
  • keep IDs, metadata, snapshots, access config, and billing/usage consistent
  • clean up hot host storage

Migration

  • move machines or state across hosts
  • support drain/maintenance workflows
  • recover from unhealthy hosts
  • migrate images/snapshots across clusters/regions
  • design for live or offline migration depending on runtime choice

Nodes / Clusters / Capacity

  • host registry, cluster model, health checks
  • scheduler with quota/capacity accounting
  • bin-packing or placement strategy
  • drain/quarantine/repair flows
  • add/remove hosts without rewriting the system
  • path to 10, 100, 1,000, 100,000, and millions of sandboxes

Access / Networking

  • SSH
  • browser terminal
  • command execution
  • file upload/download/manage
  • secure HTTPS port proxy with WebSocket support
  • auth-protected/shareable links with revocation/rotation
  • safe defaults against accidental public exposure

Control Plane / Operations

  • accounts/auth/API keys
  • sandbox lifecycle API
  • full web dashboard
  • API, CLI, SDK or typed client
  • logs/metrics/health/status
  • operation history
  • reconciliation/orphan cleanup
  • deploy/rollback/migrations
  • cost and usage tracking
  • security/threat model

What to Show at the End

  • demo of real sandbox creation and usage
  • command/file/SSH/proxy flow
